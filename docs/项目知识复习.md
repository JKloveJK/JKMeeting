## 1. C++ core：跨端音频计算边界

### 概念

跨端 core 只保存可跨平台复用的纯计算能力，例如 PCM 校验、重采样、增益和时间戳传递。它不应依赖 `AVFoundation`、Android SDK、文件系统、网络或 UI。

### 本项目实现

- 位置：`core/`
- 构建：CMake / CTest
- 核心类型：`AudioFrameView`、`OwnedAudioFrame`、`AudioProcessor`

### 关键设计：借用输入，拥有输出

```text
AudioFrameView  → 借用调用者 PCM 内存，只在函数调用期间读取
OwnedAudioFrame → 使用 vector 持有处理结果，调用者可安全保留
```

这种划分避免了 core 长期持有平台侧内存，也避免把输出生命周期交给输入缓冲区。

### 验证证据

```sh
make test-core
```

已通过 CTest，覆盖正常重采样与数值边界。

### 自测问题

1. 为什么 `AudioFrameView` 不应该保存到成员变量？
2. 为什么输出不能仅返回原始 `int16_t*`？
3. 哪些代码一旦包含平台 SDK 就不应继续放在 `core/`？

## 2. ObjC++ bridge：Swift / Foundation 与 C++ 的边界

### 概念

Swift 不能直接导入 C++ 头文件。ObjC++ 文件（`.mm`）可以同时使用 Objective-C / Foundation 和 C++，因此适合作为唯一 bridge。

### 本项目数据流

```text
Swift Data → NSData → JKMeetingCore.mm → AudioProcessor
                                  ↓
              JKMeetingAudioFrame ← NSData ← OwnedAudioFrame
```

### bridge 的职责

- 校验 S16LE PCM 字节数、采样率、声道数和帧对齐；
- 将 `NSData` 复制进对齐的 C++ 样本容器；
- 调用 C++ core；
- 将输出封装为不可变 `JKMeetingAudioFrame`；
- 将失败转换成公开 `NSError` domain 和错误码。

### 错误契约

`JKMeetingCoreErrorDomain` 与 `JKMeetingCoreErrorCode` 在 header 公开，避免 Swift 依赖 `.mm` 私有实现。

### 验证证据

```sh
make test-apple-bridge
```

已验证正常 PCM 重采样与非法字节长度拒绝。

### 自测问题

1. 为什么 bridge 应复制输入 PCM，而不是把 `NSData.bytes` 直接长期交给 C++？
2. 为什么错误 domain / code 应放在 `.h` 而不是 `.mm`？
3. bridge 为什么不应承担录音、上传或 UI？

## 3. Swift CoreProcessor：类型化的应用层接口

### 概念

Swift 业务层不应该感知 `NSError` 的 domain 和数字 code，而应通过领域错误处理失败。

### 本项目实现

- 位置：`apple/Shared/CoreProcessor.swift`
- 输入：`Data`、采样率、声道数、目标采样率、时间戳。
- 输出：`ProcessedAudioFrame`。
- 错误：`invalidPCM`、`processingFailed`、`allocationFailed`、`unexpectedBridgeError`。

### 测试场景

```text
输入：[0, 1000, 2000, 3000]，4 Hz，单声道
操作：重采样至 2 Hz
预期：[0, 2000]，2 Hz，单声道，timestamp = 42
```

另有三字节 PCM 输入，预期映射为 `.invalidPCM`。

### 验证证据

- macOS XCTest 已通过。
- iOS Simulator 已完成工程构建与测试启动验证；最终统一验证仍需写入 `Makefile`。

### 自测问题

1. 为什么 `CoreProcessor` 是 facade，而不是直接把 `JKMeetingCore` 暴露给 SwiftUI？
2. 为什么 `ProcessedAudioFrame` 应为不可变值类型？
3. 何时应该新增 Swift 领域错误，何时保留原始错误信息？

## 4. Apple 双端工程：共享实现与独立验证

### 工程结构

```text
apple/
├── project.yml                 # XcodeGen 唯一工程声明来源
├── Bridge/                      # ObjC++ bridge
├── Shared/                      # Swift facade + C++ / ObjC++ 编译边界
├── App/                         # iOS / macOS 共享 SwiftUI 页面
├── AppTests-iOS/                # iOS 独立 XCTest
└── AppTests-macOS/              # macOS 独立 XCTest
```

### 核心取舍

- iOS 和 macOS 各有 App target；
- 两端分别有 Shared framework 和 XCTest target；
- XCTest 依赖 Shared framework，而不是将 SwiftUI App 作为测试宿主；
- CMake 仅做 core / bridge 独立验证；Xcode 直接编译对应 C++ / ObjC++ 源，不链接 CMake 产物。

### 为什么不能让 XCTest 直接测 App target？

初版 hosted XCTest 会启动 SwiftUI App 生命周期，测试可能停在 `Testing started`。将业务 / bridge 代码移至 Shared framework 后，测试无需启动 UI 进程，依赖边界更清晰。

### XcodeGen 与构建目录

- `project.yml` 是唯一可编辑工程来源；
- `.xcodeproj` 由 XcodeGen 生成；
- Xcode 构建目录使用 `apple/xcode-build/`；
- CMake 构建目录使用 `apple/cmake-build/`；
- 必须分离，避免两套构建系统相互污染产物。

### 自测问题

1. 为什么 Xcode target 不应链接 CMake 静态库？
2. 为什么 iOS / macOS 需要独立 XCTest bundle？
3. Shared framework 解决了什么测试宿主问题？

## 5. iOS 黑边：Launch Screen 与设备尺寸能力

### 现象

SwiftUI 页面内容只显示在中间，四周或上下出现黑边。

### 根因

`Info-iOS.plist` 缺少 `UILaunchScreen`。iOS 会将 App 当作旧尺寸兼容应用，采用 legacy viewport 渲染，而不是完整现代设备尺寸。

### 修复

```xml
<key>UILaunchScreen</key>
<dict/>
```

### 验证证据

重新生成工程、构建、安装并启动 iPhone 17 Pro Simulator 后，截图确认黑边消失。

### 自测问题

1. 为什么没有启动屏幕配置会影响运行时 viewport？
2. 这个问题和 SwiftUI 的 `padding()` 或 Auto Layout 有何区别？

## 6. 本地服务端拓扑：数据库、对象存储与队列

### P0 目标

```text
客户端完成录音
  → 创建录音记录
  → 通过预签名 URL 上传到 S3
  → 上传确认
  → Redis 投递异步转写任务
  → Worker 调用 ASR
  → 查询转写与回放 URL
```

### 组件职责

| 组件 | 用途 | P0 中的数据 |
| --- | --- | --- |
| PostgreSQL | 事务性元数据与状态机 | recording id、状态、时长、文本、错误信息 |
| S3 兼容对象存储 | 音频二进制文件 | 原始音频对象 |
| Redis | 异步任务队列 | 转写任务 |
| Go API | 同步 HTTP 边界 | 创建、完成、查询、回放 URL |
| Go Worker | 异步任务执行 | 调 ASR、更新状态 |

### 对象存储替换决策

P0 原计划指定 MinIO，但 2026-09-29 实测：

- `minio/minio` Docker Hub 仓库不可拉取；
- `quay.io/minio/minio` 匿名拉取返回 `401 Unauthorized`。

经用户确认，本地对象存储切换为实测可拉取的 `chrislusf/seaweedfs:3.68`。SeaweedFS 以单容器形式提供 S3 兼容 API；Go API 使用标准 S3 预签名 PUT / GET URL，不依赖 SeaweedFS 私有 API。完整决策见 ADR 0004。

### 已验证的服务端闭环

```text
POST 创建录音
  → PostgreSQL 创建 created 记录
  → 返回 SeaweedFS 预签名 PUT URL
  → 客户端直传对象
  → POST complete 验证对象存在
  → created → uploaded + outbox 同事务
  → dispatcher 原子认领 outbox
  → Redis / asynq 写入转写任务
  → Worker 以 lease token 认领任务
  → whisper.cpp 转写
  → transcribing → done + transcript
  → GET 查询状态 / GET 回放 URL
```

outbox 的价值：数据库状态迁移与“需要投递的任务”同时落库；即使 API 进程在事务提交后崩溃，未投递事件仍能被后续 dispatcher 找到，而不是永久丢失。

### 本次异步链路的关键经验

- `complete` 不能只派发一条最早的 pending outbox，否则历史遗留事件会让新录音长期停在 `uploaded`；当前改为 `DispatchAll()`，在一次确认请求中清空可派发事件。
- Worker 的实际 ASR 推理约为几十毫秒；此前一分钟级冒烟失败来自轮询等待未派发任务，而不是 Whisper 推理慢。
- 每次任务认领都生成 lease token；写入 `done`、`failed` 或重试释放时都必须匹配该 token，避免旧 Worker 在 lease 过期后覆盖新 Worker 的结果。

### 自测问题

1. 为什么音频上传不应经过 Go API 代理？
2. 为什么上传确认应在文件上传后进行？
3. 为什么状态迁移要用条件更新而不是先查后改？
