## 背景

P0～P2 已经打通“录音 → 上传 → 转写 → 回放”，但转写结果只是一段纯文本，用户无法快速知道会议的结论、谁要做什么，也无法跨会议检索。P3 的目标是把音频文件变成**可评测的结构化知识**。

路线文档的验收条件：

- 摘要准确率 ≥ 80%；
- 连续 50 次调用无格式崩溃；
- 端到端 P95 < 8 秒；
- MCP Server 能被真实客户端加载。

路线文档同时提醒：难点不在“调用 chat API 拿到一段字符串”，而在上下文预算、输出格式稳定性、失败重试、工具调用降级和可评测性。

## P3-1 范围

1. **LLM 适配层**：
   - 通过 OpenAI 兼容的 `/v1/chat/completions` 调用本机 `llama-server`；
   - 用 JSON Schema 约束解码（`response_format`）保证输出可解析；
   - 服务端再做一次 schema 校验，校验失败按“格式错误”重试。
2. **结构化纪要**：转写进入 `done` 后，通过事务 outbox 异步投递分析任务（独立的 asynq 队列）。产出：
   - 摘要；
   - 决议列表；
   - 待办（内容、负责人、截止时间，负责人未知时为空）；
   - 参会人观点（人名 → 观点列表）。
3. **上下文预算**：按 token 估算转写长度。超过预算时先分段抽取，再合并（map-reduce），不能静默截断。
4. **可靠性**：
   - 超时、5xx 和格式错误可以重试，带指数退避和次数上限；
   - 并发上限用来保护本机推理资源；
   - 记录每次调用的 prompt / completion token 数和耗时，用于成本统计。本地模型的成本按 token 记账，换算成金额时假设外部单价，并在报告中说明。
5. **接口**：`GET /v1/recordings/{id}/insights` 返回分析状态（`none` / `pending` / `processing` / `ready` / `failed`）和结构化结果。
6. **评测**：
   - 固定 20 条输入；
   - 评测工具运行全集，输出准确率、格式成功率、延迟分布和 token 统计；
   - 支持“文本模式”（直接把标准转写交给 LLM，隔离 ASR 误差）和“音频模式”（`say` → 完整链路）。

## P3-1 非目标

- 不做说话人分离（diarization）。人名只能来自转写文本，所以合成脚本里由说话人自报姓名或相互称呼。
- 不做客户端界面，P3 只交付服务端能力和评测。
- 不做 LLM-as-judge：准确率用可复现的规则匹配计算，不用模型给自己打分。
- 不接入外部 LLM API。

## P3-1 验收标准

| 编号 | 标准 | 证据 |
| --- | --- | --- |
| E1 | 适配层在超时、5xx、格式错误时按上限重试，并发上限生效，每次调用都记录 token 与耗时 | `go test`（fake LLM 服务） |
| E2 | 转写完成后自动产出纪要；分析失败不影响转写状态；接口返回状态与结果 | `go test` + 冒烟 |
| E3 | 文本模式下，评测集的**要点召回率** ≥ 80%（定义见下） | 评测报告 |
| E4 | 连续 50 次结构化调用 0 次格式失败（重试前统计，格式错误计为失败） | 评测报告 |
| E5 | 单条会议结构化抽取 P95 < 8 秒（从任务开始到结果写库）；未达标时报告瓶颈与可选方案，不调整门槛 | 评测报告 |
| E6 | 音频模式跑通至少 5 条，并报告 ASR 误差对召回率的影响 | 评测报告 |

**要点召回率的定义**：

- 每条评测输入的标准答案包含若干“要点”：每条决议、每个待办（含负责人）、每位参会人的主要观点。
- 每个要点配有一组关键词，每个关键词都必须命中，单个关键词可以用 `|` 写同义词。只在**对应类别**里查找：决议只查 `decisions`；待办只查 `action_items[].task`，并要求 `owner` 包含负责人；观点只查同一 `speaker` 的 `points`。
- 实施修正（2026-10-23）：初稿写的是“模型输出中任一字段命中即覆盖”，实现时改为按类别严格匹配。按类别命中的一定也是任一字段命中，所以严格口径的召回率是初稿口径的下界，门槛没有降低；同时能暴露“待办被写进决议”这类分类错误。
- 召回率 = 覆盖的要点数 / 要点总数，对全集求总体比例。
- 关键词随标准答案一起由用户审核。

## P3-2 范围（2026-10-23 补充）

1. **索引**：转写进入 `done` 时，在同一事务登记索引任务。Worker 把转写按句子切块（每块约 300 字，相邻块重叠 1 句），调用本机 bge-m3 生成 1024 维向量后写入 pgvector。重复执行结果相同（先删后写，在同一事务内）。
2. **问答**：`POST /v1/ask`，传入问题和可选的 `top_k`（默认 5，上限 10）：
   - 先把问题向量化，用余弦距离检索 top-k 块；
   - 再让 LLM 只根据这些块作答，输出 JSON：答案、引用的块编号、资料是否不足；
   - 服务端校验引用必须属于本次检索结果，越界的引用直接丢弃并记日志；
   - 返回答案和引用（录音 ID、块序号、原文片段、距离）。
3. **评测**：`server/eval/p3/rag-questions.json` 收录 AI 起草的问题（含 2 条评测集中无答案的问题），每题标注期望的会议和答案关键词，与 P3-1 答案一并由用户审核。

### P3-2 非目标

- 不做混合检索（BM25）、重排模型、多轮对话或流式输出。
- 不做按用户隔离的权限（P0 仍为单用户）。

### P3-2 验收标准

| 编号 | 标准 | 证据 |
| --- | --- | --- |
| R1 | 转写完成后自动建索引；重复执行不产生重复块；索引失败不影响转写和纪要 | `go test`（含数据库） + 冒烟 |
| R2 | 检索命中率：期望会议出现在 top-5 引用候选中的比例 ≥ 90% | 评测报告 |
| R3 | 引用合法性：返回的引用 100% 属于本次检索结果 | 单测 + 评测报告 |
| R4 | 有答案的问题，答案关键词命中率 ≥ 80%（初步，待审核） | 评测报告 |
| R5 | 无答案的问题标记“资料不足”，不编造 | 评测报告 |
| R6 | 记录问答延迟（P50 / P95）与 token 消耗；P95 沿用 8 秒门槛，未达标时报告瓶颈 | 评测报告 |

## 依赖与风险

- 磁盘剩余约 35 GB，模型约占 5.3 GB。
- 7B 模型在 M1 Pro 上的生成速度预计约 20 token/s，E5 的 8 秒门槛有风险，需要实测后再定优化方向（缩短输出、换用更小的模型、分段并行）。
- 合成评测集由 AI 起草，存在“出题人和答题人同源”的偏差。标准答案必须经用户审核，最好再补几条真实会议文本。
