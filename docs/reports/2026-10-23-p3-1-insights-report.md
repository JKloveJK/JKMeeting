# P3-1 LLM 结构化纪要评测报告（初步）

- 关联：[P3 需求](../requirements/2026-10-23-p3-agent-pipeline-requirements.md)、[P3-1 方案](../plans/2026-10-23-p3-1-structured-insights-implementation.md)
- **状态：初步。** 评测集的标准答案和关键词由 AI 起草，用户尚未审核；审核前，E3 / E6 的数字不能作为正式验收依据。

## 1. 环境

- Apple M1 Pro，10 核，32 GB 内存，macOS 27.0（arm64）。
- `llama-server`（Homebrew llama.cpp，版本 0.5.0 build 11146），参数为 `-c 8192 -np 1 -ngl 99`，Metal 全量卸载。
- 模型：Qwen2.5-7B-Instruct Q4_K_M（bartowski，4.68 GB，sha256 已校验）。温度 0，`response_format` 为 `json_schema`（strict）。
- ASR：whisper-server，ggml-base 模型，Metal。
- **噪声说明**：测量期间系统 1 分钟负载在 100～190 之间，主要来自本仓库之外的进程。延迟的绝对值偏保守。

## 2. 输入与命令

| 实验 | 输入 | 命令 | 原始数据 |
| --- | --- | --- | --- |
| 文字模式 | `server/eval/p3/cases.json`，20 段合成中文会议（每段 6 句、约 250 字），共 105 个要点 | `go -C server run ./cmd/insighteval -cases eval/p3/cases.json -out ../output/p3-1-text-eval.jsonl` | `output/p3-1-text-eval.jsonl`、`output/p3-1-text-eval-summary.json` |

| 音频模式（全链路） | 5 条用例（c01、c02、c05、c08、c14），`say -v Tingting` 合成 38～44 秒语音，AAC 64 kbps，经 API 上传 | `server/scripts/p3-audio-eval.sh` | `output/p3-1-audio-eval.log`、`output/p3-1-audio-20261023-153629.{recordings,transcripts.jsonl,jsonl}` |

**评分口径**：按类别严格匹配。决议只查 `decisions`；待办查 `action_items[].task`，并要求 `owner` 一致；观点查同一 `speaker` 的 `points`。关键词全部命中才算覆盖，单个关键词可用 `|` 写同义词，比较前去掉标点和空白。不使用 LLM 评判。

## 3. 数据

### 3.1 文字模式（E3、E5）

| 指标 | 20 条单轮 | 50 次连续调用 |
| --- | --- | --- |
| 要点召回率 | **88.6%**（93/105） | **88.2%**（231/262） |
| 决议 / 待办 / 观点召回率 | 91.7% / 90.5% / 81.5% | 92.2% / 89.5% / 80.6% |
| 调用失败 | 0 | 0 |
| 延迟 P50 / P95 / 最大 | 12.5 / **15.5** / 16.4 s | 13.3 / **16.3** / 17.6 s |
| 平均 prompt / completion token | 300 / 269 | 301 / 270 |

20 条单轮的延迟（ms，升序）：9021, 10341, 10684, 10910, 11039, 11288, 11540, 12131, 12280, 12529, 12577, 13059, 13242, 13837, 13896, 14025, 14898, 15129, 15495, 16420。

漏召回共 12 个要点，可分为两类：

- **类别错放（主要）**：
  - c03：“林芳更新岗位描述”被写进了 `decisions`，没有出现在 `action_items`；
  - c14：两条决议都被写成了待办，`decisions` 为空；
  - c06：“迭代评审定在周五”没有被识别为决议。
- **观点遗漏**：c02 赵敏“值班手册要补充”、c08 萧峰“冻结 schema 变更”、c16 陆明“占位图”。这几条都是一句带过、没有被讨论的意见。推测（待验证）：模型倾向于只保留有明确结论的发言。

按需求初稿的“任一字段命中”口径，分数只会更高：严格口径命中的要点，在宽松口径下一定也命中。

### 3.2 格式稳定性（E4）

50 次连续调用：

- 共 50 次 HTTP 尝试，**0 次格式失败**（重试前统计），0 次重试，0 次最终失败；
- completion 长度 190～364 token。

`json_schema` 约束解码保证了语法合法；Go 侧校验（`summary`、`task`、`speaker` 不能为空，四个字段必须存在）也没有被触发。

### 3.3 延迟瓶颈（E5 未达标）

`llama-server` 自带的计时（`/tmp/jk-llm.log`，`print_timing`）：

| 阶段 | 实测 |
| --- | --- |
| prompt 处理 | 130～185 token，耗时 0.6～1.1 s（160～210 token/s） |
| 生成 | 约 **23～24 token/s**（每 token 41～43 ms） |
| 典型一次调用 | 270 个输出 token × 42 ms ≈ 11.3 s，加上 prompt 约 0.8 s |

**结论**：约 90% 的耗时在逐 token 生成上，瓶颈是 M1 Pro 的内存带宽（Q4_K_M 7B 每生成一个 token 都要读一遍约 4.4 GB 权重）。数据库、队列和 HTTP 开销都在毫秒级。按当前生成速度，要在 8 秒内完成，输出必须压到约 170 token 以内，或者生成速度提高约 1.6 倍。

可选方案（**未实施**，门槛不变；方案的取舍由用户决定）：

| 方案 | 预期效果 | 代价 |
| --- | --- | --- |
| 换 Qwen2.5-3B-Instruct Q4_K_M | 生成速度约翻倍 | 召回率预计下降，需要重新评测；需再下载约 2 GB |
| 压缩输出（摘要限制在 2 句以内，观点只保留有结论的发言，字段名缩短） | 输出 token 减少 30～40% | 观点召回率可能进一步下降 |
| 投机解码（`llama-server -md` 加 Qwen2.5-0.5B 草稿模型） | JSON 这类高可预测输出通常能加速 1.5～2 倍 | 多占约 0.5 GB 内存，需要实测接受率 |
| 外部 API | 延迟取决于服务商 | 涉及费用和隐私边界，需要用户另行确认 |

### 3.4 音频模式（E6）

| 用例 | 音频时长 | 转写字形 | 召回（全链路） | 转写中仍可找到的要点（简体化后） |
| --- | --- | --- | --- | --- |
| c01-release | 44.2 s | 繁体 | 3/5 | 3/5 |
| c02-incident | 42.0 s | 繁体 | 0/5 | 2/5 |
| c05-design | 41.1 s | 繁体 | 2/6 | 3/6 |
| c08-migration | 40.2 s | 简体 | 1/6 | 2/6 |
| c14-appstore | 37.8 s | 繁体 | 2/6 | 2/6 |
| **合计** | | | **8/28（28.6%）** | **12/28（42.9%）** |

- 状态推进：每条都从 `done/processing` 进入 `done/ready`，用时 16～21 秒，没有失败和卡住；`analysis_ms` 的 P50 为 17.1 s，P95 为 21.4 s。音频模式比文字模式慢，原因是 5 条录音同时上传，Whisper 和 llama-server 在同一块 GPU 上交替推理。
- **误差分解**（同 28 个要点，只看关键词和人名是否还留在转写文本里）：

  | 文本来源 | 能找到的要点 |
  | --- | --- |
  | 标准转写 | 28/28 |
  | ASR 原始输出 | 2/28 |
  | 繁转简后 | 12/28 |

  这说明：
  1. **繁简字形**：Whisper base 在 5 条里有 4 条输出繁体，损失约 10 个要点。这部分不是 LLM 的问题，属于评分时的字形不一致。不过 LLM 只部分把输出转成了简体，所以实际召回也受到影响。
  2. **同音字和人名错误**：还剩 16 个要点的关键词在转写里已经错了，例如：
     - 灰度→灰毒，连接池→連接持，权限→全縣，迁移→千仪，详情页→響情夜；
     - 许晴→許情，孙丽→孫力，萧峰→消风，范军→范君；
     - “韩梅梅说”被识别成“還沒沒說”。

     这类错误 LLM 无法凭空恢复。
  3. 在剩下的 12 个可恢复要点中，LLM 召回了 8 个（67%），低于文字模式的 88%。原因是转写里的错字和断句让模型更难判断类别和说话人。

## 5. 成本（按 token 记账）

- 每段会议（约 250 字，40 秒）平均 301 个 prompt token、270 个 completion token，1 次 LLM 调用。
- 本地推理没有 API 费用，成本体现为 GPU 占用时间：每条约 13 秒。
- 按**假设**的外部单价（输入每百万 token 2 元、输出每百万 token 8 元，仅用于数量级换算，不代表任何具体服务商）：每段约 0.0028 元。真实一小时会议的转写约 1.5 万字，会触发 map-reduce（3 段加 1 次合并），成本按 token 线性增长。

## 6. 结论与下一步

1. 结构化纪要的格式稳定性已经可靠（约束解码加 Go 侧校验）。文字模式召回率约 88%，主要误差是类别错放。可以在提示词里加入反例，或者在 schema 中让待办强制带负责人，再复测。
2. E5 的瓶颈已定位为生成速度。是否换小模型、压缩输出或启用投机解码，需要用户决定。
3. 音频模式的瓶颈在 ASR，不在 LLM。可选方向：
   - whisper-server 请求带简体中文 `prompt`，统一输出字形；
   - 加入人名热词；
   - 换 small 或 medium 模型。

   这些改动属于转写模块，需要单独立项。
4. 评测集答案审核完成后，重跑 `make eval-insights`，把本报告的数字从“初步”转为正式结论。
5. 单段超过上下文预算时的 map-reduce 只有单测覆盖（1200 次重复内容不丢失），还没有用真实长会议实测。
