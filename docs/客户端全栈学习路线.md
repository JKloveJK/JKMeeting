# 客户端工程师的全栈学习路线：服务端 / 音视频 / Agent / 安卓

> 面向对象：iOS（Swift / Objective-C）背景，希望补齐服务端、音视频、Agent、安卓端四块能力。
> 结论导向：**可以用一个项目覆盖四个方向，但必须按依赖串行推进，且"深度"需要主动制造条件才能获得。**
> 当前状态：技术栈已锁定，P0 设计已定稿。

---

## 0. 先给结论

| 问题 | 答案 |
| --- | --- |
| 一个项目能覆盖全部四块吗？ | **能覆盖广度（约 80%）**，深度必须靠主动加压补齐 |
| 覆盖的前提是什么？ | ① 项目有真实使用场景；② 一块一块串行接；③ 每块有可量化验收指标 |
| 只靠一个项目的风险？ | 每块都停在"会调用 API"的层次，面试或转岗时讲不出细节 |
| 怎么补深度？ | 主项目 + 专项 Spike（见第 6 节） |
| 时间尺度？ | 每周 8–10 小时，总计 **6–7 个月** |

这条路的本质区别：

- ❌ **横向铺开**：这周学 Go，下周学 Compose，再下周学 WebRTC。三周后全部忘光，因为没有真实需求把它们缝在一起。
- ✅ **纵向贯通**：一个产品，一条真实链路，从端到端打通。每个技术选型都是被真实约束逼出来的。

**关键机制：约束驱动深度。** 没有真实约束（并发、延迟、弱网、成本），你就只会写 CRUD。所以项目设计的第一优先级是——**给自己制造约束**。

**四块的深度获取方式不同，这一点必须说清**：

| 能力 | 深度从哪来 |
| --- | --- |
| 服务端 | **加压 + 加观测**（压测、故障注入、大数据量）—— 不靠加功能 |
| 音视频 | **指标化 + 调优**（RTF、首帧、丢包恢复） |
| Agent | **可评测**（固定评测集，量化准确率与延迟） |
| 安卓 | **对比**（与 iOS 同场景指标对比，定位差异根因） |

## 1. 项目选题

### 1.1 选题必须满足的 3 条标准

1. **天然横跨四块**：任何一块缺失，产品就跑不起来。这样你就没法跳过。
2. **你自己是真实用户**：哪怕只有一个用户。否则做到 60% 就会因为"没人用"而放弃。
3. **能塞进真实约束**：有并发、有延迟、有数据管道、有成本。

### 1.2 选题：会议语音助手（JKMeeting）

一句话：**iOS + 安卓双端录音，核心逻辑走 C++ core → 服务端存储与转写 → Agent 生成纪要、待办与可检索知识库。**

为什么这个选题对你特别合适：你的日常工作就在腾讯会议 IM 方向。产品逻辑、数据形态、边界条件你都熟，注意力可以全部放在**技术栈本身**上，而不是同时猜业务。

### 1.3 它为什么天然覆盖四块

| 能力块 | 在项目里对应什么 | 为什么绕不过去 |
| --- | --- | --- |
| 音视频 | 采集 → C++ core 处理 → 编码 → 传输 → 服务端转码 → 回放 | 不做就没有音频输入，整个产品不存在 |
| 服务端 | 鉴权、上传、对象存储、任务队列、数据库、API、部署、可观测 | 音频得有个地方落，转写总得有个进程跑 |
| Agent | ASR → LLM 结构化摘要 → 向量检索问答 → 工具调用 | 这是产品的核心价值，不做就只是个录音 App |
| 安卓端 | Kotlin + Compose 只画 UI，逻辑走同一份 C++ core | 第二个平台是检验抽象是否成立的唯一手段 |

四条链路**串联**，这是这个选题最大的优点。

## 2. 四层能力全景对照表

| 层 | 项目模块 | 关键知识点 | 验收指标（目标值，自行标定） |
| --- | --- | --- | --- |
| 客户端 / core | C++ core + 双端壳 | 帧管理、重采样、状态机、ObjC++ / JNI 桥接、CMake | core 在 macOS 单测通过；两端行为一致；core 处理耗时占比 < 20% |
| 音视频 | 采集 / 编码 / 转码 / 回放 | PCM、AAC/Opus、封装容器、WebRTC、SRT、HLS、抖动缓冲、弱网对抗 | 首帧 < 1.5s；30% 丢包下语音仍可懂；转码 RTF < 1 |

## 3. 分阶段路线

### P0 · 跨端骨架与最小闭环（4 周）

**目标**：同时打穿两条最容易卡死的链路 —— C++ core 的跨端构建，与云侧的端到端管道。

- 建 repo：`core/`（C++ CMake）+ `ios/` + `android/` + `server/`（Go module）
- **C++ core 第一个 API**：`AudioFrame` / `AudioProcessor`，只做重采样 + 增益，不引任何第三方库
- iOS：ObjC++ 桥接 + `AVAudioEngine` 采集（**不能用 `AVAudioRecorder`**，它拿不到 PCM）
- 服务端：4 个接口 + PostgreSQL + Redis + MinIO + asynq worker + whisper.cpp 转写
- Harness 最小集：`AGENTS.md` + `Makefile`（`make verify` / `make load`）+ pre-commit

**验收**：录 30 秒 → 经 core 处理 → 上传 → 转写出文字 → 回放；报出四个基线数（上传 P95 / 转写 RTF / 松手→出文字 / core 处理耗时占比）。

**执行顺序（最大不确定性优先）**：core 构建打通（硬时间盒 3 天）→ 起底座 → 通接口 → 通 ASR → 通采集 → 对接。

详见 [P0 设计](plans/2026-09-29-p0-minimal-loop-design.md)。

---

### P1 · 服务端纵深（4 周）

**目标**：不是加接口，是**加压与加观测**。同一个服务，从"能跑"推到"能扛、能看、能演进"。

- 部署：多阶段 Dockerfile → 云主机 + TLS + 域名
- 可观测：OpenTelemetry（trace / metrics）+ Prometheus + 慢查询定位
- 压测：k6 或 wrk，从 100 → 1000 并发，出曲线与拐点
- 调优：`pgxpool` 连接池、索引、N+1 消除、`EXPLAIN ANALYZE`
- 韧性：故障注入（杀 Postgres / Redis / MinIO）、限流、背压、队列堆积行为
- 数据量：造 100 万条 recordings，验证索引不退化

**验收**：达到 [服务端深度阶梯](plans/2026-09-29-server-depth-plan.md) 的 **L4** —— 有压测报告，P95 是调出来的而不是碰巧的。

**为什么排在音视频之前**：P0 刚把手感养起来，趁热打铁成本最低；而且服务端纵深全是确定性工程动作，适合放在音视频那种高不确定性阶段之前把地基做扎实。两者互相独立，若你更想先推音视频，把 P1 / P2 对调成本为零。

---

### P2 · 音频管道（4–5 周，音视频重心）

**目标**：把音视频能力做扎实，全链路可测量。

- C++ core 内：帧与时间戳、重采样、增益、静音检测
- 编码：引入 Opus（纯 C，CMake 友好），替换平台原生编解码
- 落文件与回放链路、丢帧与抖动处理
- 服务端转码：FFmpeg → HLS、多码率（同时是服务端并发能力的延伸）

**验收**：RTF < 1；core 处理耗时占比 < 20%；回放多码率可切换。

---

### P3 · Agent 管道（3–4 周）

**目标**：把"音频文件"变成"结构化知识"。

- LLM 结构化输出：摘要、决议、待办、参会人观点
- 向量化 + RAG：让用户能问"上次谁提到过这个方案？"
- Tool Calling + **MCP Server**：把你自己的服务暴露成 MCP 工具（你有 D2C 与 MCP 的现成经验，性价比极高）
- 评测集：固定 20 条输入，量化准确率与延迟
- 服务端侧：LLM 调用的重试、限流、成本统计

**验收**：摘要准确率 ≥ 80%；连续 50 次调用无格式崩溃；P95 端到端 < 8s；MCP Server 能被真实客户端加载。

**最容易踩的坑**：只做"调 chat API 拿一段字符串"。真正的难度在上下文预算、输出格式稳定性、失败重试、工具调用降级、以及**可评测**。

---

### P4 · 安卓端接入（3–4 周）

**目标**：用第二个平台检验 C++ core 的抽象是否成立 —— 这是整条路线里最重要的一次验证。

- Kotlin + Compose 只写 UI，核心逻辑通过 JNI 调同一份 C++ core
- 重点理解**差异**：生命周期、Binder、Gradle + NDK 构建、ART 与 ARC 的内存管理差异、后台限制策略
- 记录：为了让 core 支持第二个平台，API 改了多少 —— **改动量就是抽象质量的度量**

**验收**：安卓端主链路打通；**core 代码零修改或极小修改**（这是"抽象成立"的硬判据）；冷启动 < 800ms。

---

### P5 · 实时与工程化（持续推进）

- 实时流：WebRTC / SRT 推流、抖动缓冲、重传、自适应码率、弱网对抗
- 视频：FFmpeg 引入（**此时才碰交叉编译**，见 4.3）
- CI/CD：提交即构建、自动跑 core 单测与 Go 测试、自动跑评测集
- 监控告警、成本看板、压测报告
- 服务端到达 L5–L6：不停机改 schema、灰度回滚、一致性与队列语义的取舍

**验收**：首帧 < 1.5s；30% 丢包下语音仍可理解。

## 4. 技术栈选择

### 4.1 服务端语言 —— ✅ 已定：Go

选定 **Go 服务端 + Kotlin 安卓端 + C++ core**。

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Kotlin（Ktor / Spring Boot） | 与安卓同语言，一份语言心智覆盖两端；JVM 生态成熟 | JVM 较重，云原生资料不如 Go 多 | 备选 |
| **Go** | 语法极少、并发模型简单、单二进制部署、云原生生态最成熟 | 要多学一门语言，且泛型/生态表达力不如 JVM | ✅ **已选定** |

选择理由（按权重排序）：

1. **Go 的语法量小**，学习带宽主要花在并发模型、数据建模、可观测这些真正难的概念上，而不是语言特性。
2. **部署路径最短**：编译成静态二进制 → 一个 Docker 镜像，没有 JVM 运行时膨胀，本地与线上行为一致。
3. **云原生生态资料密度最高**，往上走（容器编排、可观测、网关）时阻力最小。
4. Go 的 `slog` / `pprof` / `net/http/pprof` 都是标准库自带，做服务端调优时开箱即用。

**这个决定已经锁定，后续不再回头比较。**

### 4.2 其余栈

| 层 | 选型 | 备注 |
| --- | --- | --- |
| 共享层 | **C++ core**（已定） | 只放纯计算 / 纯状态机 / 协议；平台 API 一律留在壳层 |
| iOS 壳 | SwiftUI + ObjC++ 桥接 + AVAudioEngine | 见 P0 设计 §3.6 |
| 安卓壳 | Kotlin + Compose + JNI + AudioRecord | 只绘制 UI |
| 数据库 | **PostgreSQL** | 服务端深度的主战场，见服务端深度路线 |
| 缓存 / 队列 | Redis + asynq | 同时当缓存与轻量队列 |
| 对象存储 | MinIO（本地）/ 云 OSS | 本地起步，接口保持 S3 兼容 |
| 音视频 | 平台原生 → Opus → FFmpeg | 三步走，推迟交叉编译风险 |
| Agent | 先云 API，再自写编排 | 不要把时间花在训模型上 |
| 部署 | Docker Compose 起步 | **不要上 K8s** |

### 4.3 第三方库的三步走（推迟交叉编译风险）

跨端 C++ 真正难的不是写 C++，是**第三方库的交叉编译**。FFmpeg 需要分别为 iOS（真机 arm64 + 模拟器）与 Android（arm64 + x86_64）编译，这一步能吞掉几周且学不到核心能力。

| 阶段 | 编解码方案 | 交叉编译负担 |
| --- | --- | --- |
| P0–P1 | 平台原生（AudioConverter / MediaCodec） | 零 |
| P2 | Opus（纯 C，CMake 友好） | 低 |
| P5 | FFmpeg（视频 + 全格式） | 高，但那时你有能力处理 |

### 4.4 Go 落地清单

| 关注点 | 选型 | 为什么 |
| --- | --- | --- |
| HTTP | 标准库 `net/http` + `chi` | 先理解标准库的 Handler / 中间件模型，框架只是薄封装 |
| RPC | `google.golang.org/grpc` + protobuf | 体验与 REST 的范式差异，接一条链路即可 |
| 数据库 | PostgreSQL + `pgx` / `pgxpool` | 原生协议、性能好；连接池可调是 P1 的重点 |
| 迁移 | `golang-migrate` 或 `goose` | schema 变更可版本化、可回滚 |
| 缓存 / 队列 | Redis + `asynq` | 起步用 asynq，跑顺了再考虑 NATS / RabbitMQ |
| 对象存储 | `minio-go` | S3 兼容，切云 OSS 零改动 |
| 日志 | 标准库 `slog` | 结构化日志，零第三方依赖 |
| 可观测 | OpenTelemetry Go SDK + Prometheus | 从第一天就埋 trace，别等出问题才补 |
| 配置 | 环境变量 + `koanf` | 12-factor，避免配置文件分叉 |
| 测试 | 标准 `testing` + `testcontainers-go` | 集成测试用真容器，不用 mock 骗自己 |
| 压测工具 | k6 或 `hey` / `wrk` | **P0 就要加进 Makefile**，否则全程没有性能基线 |
| 开发体验 | `air` 热重载 | 改完即生效，减少等待 |
| 部署 | 多阶段 Dockerfile → 静态二进制 | 镜像可压到 20MB 以内 |

### 4.5 安卓端落地清单

| 关注点 | 选型 | 为什么 |
| --- | --- | --- |
| UI | Jetpack Compose | 声明式，SwiftUI 心智可直接迁移 |
| 构建 | Gradle Kotlin DSL + Version Catalog + NDK/CMake | 与 Xcode 心智差异最大，要单独花时间 |
| 桥接 | JNI（配 `externalNativeBuild`） | 对应 iOS 侧的 ObjC++ 桥接 |
| 序列化 | `kotlinx.serialization` | 编译期生成，无反射开销 |
| 异步 | Coroutines + Flow | 对应 Swift 的 async/await 与 AsyncSequence |
| 架构 | ViewModel + StateFlow + 单向数据流 | 与你熟悉的 C++ ViewModel 架构思路同源 |
| DI | Hilt（Koin 起步更快） | |
| 音频 | `AudioRecord` + Media3 | 对应 AVAudioEngine / AVPlayer |

## 5. iOS 背景的迁移优势与短板

| 你的资产 | 迁移到 | 为什么快 |
| --- | --- | --- |
| ARC / 内存管理心智 | 服务端内存与性能调优、C++ 手动管理 | 你本来就理解对象生命周期 |
| 渲染管线、帧率与性能分析 | 音视频编解码、实时性优化 | 同一套"逐帧分析"的方法论 |
| 多线程与队列 | 服务端并发模型、goroutine | GCD 思维可平移 |
| Objective-C++ / C++ ViewModel | **C++ core 与 ObjC++ 桥接** | 你已经在写跨端 C++ —— 这是最大的杠杆 |
| 编译期机制偏好（宏、`NSStringFromSelector`） | 服务端代码生成、桥接层设计 | 减少运行时开销的思路通用 |
| Xcode 工程与构建经验 | CMake / Gradle | 构建系统的心智可迁移 |

| 你的短板 | 需要补什么 |
| --- | --- |
| Linux / Shell | 进程、文件系统、权限、systemd、日志排查 |
| 网络 | TCP/TLS、HTTP/2、gRPC、代理与超时重试 |
| **数据** | **关系建模、索引、事务隔离级别、锁、N+1、EXPLAIN** ← 服务端深度的主战场 |
| 分布式基础 | 幂等、最终一致、任务队列语义、限流、背压 |
| 构建系统 | Gradle + NDK（与 Xcode / CMake 心智差异最大） |
| JVM 生态 | 若后续接触 Kotlin 服务端，需补 JVM 内存模型与 GC |

## 6. 专项 Spike 清单（补深度用）

主项目之外，做 3–5 个短平快的专项，每个 3–5 天，产出一篇带数据的结论。作用是**把"我会用"变成"我知道边界在哪"**。

| Spike | 产出 |
| --- | --- |
| **PostgreSQL 索引与事务隔离** | 同一查询在有无索引下的 `EXPLAIN ANALYZE` 对比；不同隔离级别下的并发行为 |
| **压测与调优** | 连接池大小 vs 并发数的吞吐曲线，找到拐点并解释原因 |
| **FFmpeg 转码参数对比** | 不同码率/预设下的 RTF 与体积-画质曲线 |
| **自写一个 MCP Server** | 能被真实客户端加载，附带工具描述设计与失败处理 |
| **双端同场景性能对比** | iOS 与安卓的启动 / 采集 / 播放指标对比，定位差异根因 |

## 7. 明确不要做的事

- ❌ **一上来学 K8s / 微服务 / Service Mesh**：这些是规模问题，不是入门问题
- ❌ **消息队列选型对比**（RabbitMQ vs Kafka vs NATS）与**分布式事务**：单服务规模下学不到真东西
- ❌ **用低代码 / 全托管 Serverless**：把要学的东西全部遮住了
- ❌ **做纯 CRUD 后台**：没有约束，学不到任何工程能力
- ❌ **把平台 API 塞进 C++ core**：会得到一堆 `#ifdef`，比两份实现更难维护
- ❌ **四块并行开工**：会同时卡在四个"就差一点"
- ❌ **"学完再动手"**：永远学不完，且没有反馈回路

## 8. 第一周就能开始的动作

1. 建 repo（`core/` + `ios/` + `android/` + `server/`），README 写死 MVP 的一条主链路和**不做什么**
2. `docker compose` 起 PostgreSQL + Redis + MinIO，确认能连上
3. **打穿 C++ core 构建链路**：CMake + macOS 单测 + iOS 真机调用（**时间盒 3 天**）
4. `Makefile` 里加 `make verify` 与 `make load`（压测），从第一天就有性能基线
5. 写下你打算量化的 **4 个指标**：上传 P95、转写 RTF、松手→出文字、core 处理耗时占比

## 9. 怎么证明你学会了（能力证据链）

代码能跑不等于能力可迁移。三层证据的含金量完全不同：

| 层级 | 内容 | 说服力 |
| --- | --- | --- |
| 第 1 层 | "我实现过这个功能" | 最低，几乎无法区分于抄教程 |
| 第 2 层 | "我把 P95 从 2.1s 降到 480ms，这是压测报告与 trace" | 高，无法伪造 |
| 第 3 层 | "同类方案我对比过三种，在 X 约束下我选了 B，因为…" | 最高，体现判断力 |

所以每一层能力都要沉淀**第二、三层**的证据：压测报告、火焰图、`EXPLAIN ANALYZE` 前后对比、技术选型记录。这些才是面试和内部转岗时真正被记住的东西。

---

## 10. 一句话总结

选一个你自己会用的产品，把四块能力按依赖顺序一节一节接上去，每一节都留一份带数字的证据。广度靠一个项目就够；**深度靠主动制造压力** —— 服务端加压与观测，音视频指标化，Agent 可评测，安卓做对比。
