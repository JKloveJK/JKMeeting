# 服务端深度路线：从「能跑」到「能推理」

- 日期：2026-09-29
- 关联文档：[客户端全栈学习路线](../客户端全栈学习路线.md)、[P0 设计](2026-09-29-p0-minimal-loop-design.md)
- 定位：服务端与音视频并列为学习重心

---

## 0. 核心判断

**服务端深度不来自功能数量，来自「加压 + 加观测」。**

同一套四个接口：

| 状态 | 级别 |
| --- | --- |
| 写完能跑，DB 里有数据 | L1 |
| 配 trace + 连接池 + 限流，压到 1000 并发，逐项调到 P95 达标，出报告 | L4 |

**代码量几乎不变，认知差一个数量级。**

推论：**不要靠"加接口 / 加微服务"来学服务端**，那只会增加表面积而不增加深度。要靠"加压力、加观测、加数据量"。

---

## 1. 深度阶梯 L1–L6

| 级 | 名称 | 判据（做到这个 = 到这一级） |
| --- | --- | --- |
| L1 | 能跑 | 接口功能正确，DB 有数据，客户端能跑通 |
| L2 | 正确 | 重复请求不产生脏数据；并发写不出错；事务边界清晰；错误码成体系 |
| L3 | 可看 | 一个 `request_id` 能从入口追到 DB、追到 worker；有 metrics 面板；能定位慢查询 |
| L4 | 可扛 | 有压测报告；P95 是调出来的不是碰巧的；知道拐点在哪、由什么资源决定 |
| L5 | 可演进 | 不停机改 schema；API 版本化；可灰度可回滚 |
| L6 | 可推理 | 能讲清为什么这里选 at-least-once 而不是 exactly-once；能讲清一致性的代价 |

**大多数人停在 L1。** L2 是写代码时自然获得的；**L3–L6 必须主动制造条件**，这也是本文件存在的意义。

---

## 2. 六个「不加功能」的加压动作

每个动作都要产出三样东西：**一个数、一句结论、一次改动**。没有这三样，做了等于没做。

| # | 动作 | 怎么做 | 要回答的问题 |
| --- | --- | --- | --- |
| 1 | **压测** | k6 或 `hey`，100 → 500 → 1000 并发，记录 P50/P95/P99 与错误率 | 拐点在哪？由什么资源决定（CPU / 连接池 / DB）？ |
| 2 | **故障注入** | 压测中依次 kill Postgres / Redis / MinIO | 服务是直接 500 还是优雅降级？恢复后能自愈吗？ |
| 3 | **数据量** | 造 100 万条 `recordings`，重测同一个查询 | 索引还在生效吗？深分页是否退化？ |
| 4 | **慢查询** | `EXPLAIN (ANALYZE, BUFFERS)` 逐个看接口的 SQL | 有没有全表扫、N+1、隐式类型转换？ |
| 5 | **连接池** | 固定并发，扫 `pgxpool` MaxConns 从 5 到 100 | 吞吐在哪个值饱和？超过后为什么反而下降？ |
| 6 | **队列堆积** | 灌 10 万任务后停掉 worker，观察 api 与 Redis | 内存涨多少？有背压吗？恢复后是否雪崩？ |

**这六条不需要写任何新功能**，只需要新动作。它们就是"服务端深度"的全部来源。

## 3. 时间分配（重要）

| 方向 | 占比 | 理由 |
| --- | --- | --- |
| **PostgreSQL** | **60%** | 单服务规模下，复杂度几乎全部落在数据库：索引、事务隔离级别、锁、连接池、执行计划 |
| Go 与并发 | 20% | 语法两周够用；重点在 goroutine 泄漏、context 取消、`pprof` 定位 |
| 可观测与部署 | 15% | trace / metrics / 告警 + 镜像与 TLS |
| Redis 与消息语义 | 5% | 队列语义（at-least-once）、缓存一致性 |

**明确说：Go 语言本身不是重点。** 两周之后你的瓶颈就不在语法上了，继续读语言特性收益极低。把时间挪给 PostgreSQL —— 这是本文件里最有价值的一条建议。

---

## 4. 每个阶段的对应目标

| 阶段 | 服务端目标 | 目标级别 |
| --- | --- | --- |
| **P0** | 4 个接口 + 队列 + 幂等 + `request_id` 贯穿日志 | L1、L2 大部分 |
| **P1（服务端纵深）** | 部署 + 观测 + 压测 + 调优 + 韧性 + 数据量 | **L3、L4** |
| P2（音视频期） | 转码任务的并发控制与队列优先级 | L4 延伸 |
| P3（Agent 期） | LLM 调用的重试、限流、成本统计、超时预算 | L2 / L3 复用 |
| P5 | 不停机迁移、灰度回滚、一致性取舍 | L5、L6 |

## 5. 明确不要学（现在）

- ❌ 微服务拆分、Service Mesh、K8s
- ❌ 消息队列选型对比（RabbitMQ vs Kafka vs NATS）
- ❌ 分布式事务、分布式锁的复杂变体
- ❌ Go 的高级语言特性与泛型技巧

**理由**：这些都是**规模问题**。单服务 + 单机规模下你学不到真东西，只会增加噪音和表面积。等真的需要时再学 —— 那时你手上有真实约束可以做判据。

## 6. 现在就能做的 30 分钟动作

在 P0 的 `Makefile` 里加一个目标：

```make
load:  ## 打 100 并发到创建接口
	hey -n 2000 -c 100 -m POST \
	  -H "Authorization: Bearer $(P0_TOKEN)" \
	  -H "Content-Type: application/json" \
	  -d '{"duration_ms":30000,"size_bytes":120000,"content_type":"audio/mp4"}' \
	  http://localhost:8080/v1/recordings
```

成本 30 分钟，但从 P0 起每个阶段都有性能基线。**没有基线，后面所有"优化"都是自说自话。**

## 7. 一个反直觉的提醒

服务端最容易的自我欺骗是：**"我这个服务能跑，所以我会服务端了"。**

判断标准很简单 —— 你能回答下面三个问题吗？

1. 你的服务在 500 并发时 P95 是多少？拐点出现在哪个并发数？限制它的是 CPU、连接池还是 DB？
2. 把 Postgres 停掉 10 秒，你的服务表现是什么？恢复后自动好转吗？
3. `recordings` 表有 100 万行时，列表接口的查询计划是什么？走了索引吗？

三个都答不上来 = 还在 L1。**这就是"能跑"和"能扛"之间的全部距离。**
