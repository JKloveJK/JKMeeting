# JKMeeting 问题排查记录

> 用于简短记录开发中可复用的问题原因、证据、修复方式和防回归手段。仅记录已定位且具有复用价值的问题。

## 2026-09-30：AVAudioEngine 安装 tap 时因格式不匹配崩溃

### 现象

点击“开始录音”后，进程以 `NSException` 崩溃：

```text
com.apple.coreaudio.avfaudio
Failed to create tap due to format mismatch
1 ch, 16000 Hz, Int16
```

关键调用位于 `AppleAudioCapture.start` 的 `installTap(onBus:bufferSize:format:block:)`。复现设备为 iPhone 17 Pro Simulator（iOS 26.3，`0DD711F2-54D7-4CF5-8077-DD53F77E6D8A`）。排查时该设备已安装 App 的二进制时间为 2026-09-30 11:07，早于本地构建产物（11:28）和修复后的源码（11:31）；当时运行的并非修复后版本。

### 根因

代码把处理层期望的 `16 kHz / Int16 / 单声道` 直接作为 input node 的 tap 格式。`AVAudioEngine` 的 input node 必须使用当前设备或 Simulator 提供的硬件原生输出格式；任意指定不匹配格式时，AVFAudio 会抛出 Objective-C `NSException`，Swift 的 `do/catch` 无法捕获，因此进程直接终止。

### 修复

1. `installTap` 的 `format` 改为 `nil`，让 input node 使用硬件原生格式。
2. 新增 `NativePCMFrameConverter`，在 tap 回调中通过 `AVAudioConverter` 把原生 PCM 转成 C++ core 接受的交错 S16LE 单声道数据。
3. 转换后仍保留硬件采样率，由 `CoreProcessor` 负责重采样到 16 kHz，维持 C++ core 的职责。
4. 无效硬件格式在安装 tap 前返回 `.unsupportedInputFormat`，避免进入 AVFAudio 异常路径。

### 验证

- 在上述 iOS 26.3 Simulator 运行 `AudioCaptureContractTests`：6 项通过；完整 iOS XCTest：20 项通过；macOS XCTest：20 项通过。原始输出见 `output/audio-tap-ios-test.log`、`output/audio-tap-ios-full-test.log` 和 `output/audio-tap-macos-test.log`。
- 已在崩溃设备上安装本次构建并启动成功。**录音场景验证状态：待确认。**尚未点击“开始录音”复测真实 tap，真机麦克风也未验证；不可将启动成功等同于录音闭环通过。

### 防回归

- 双端测试断言 `AppleAudioCapture.tapInstallationFormat == nil`。
- 双端测试验证 48 kHz Float32 原生 buffer 可转换为 S16LE 单声道 PCM，并保留采样率和时间戳。
- 原则：**采集节点使用硬件格式；业务处理格式在节点之外转换。不要把算法目标格式直接传给 input node 的 `installTap`。**

## 2026-10-21：PostgreSQL 容器在 100 万行并行扫描 / VACUUM 时报 `/dev/shm` 空间不足

### 现象

在向 `recordings` 表注入 100 万行数据并执行 `VACUUM ANALYZE recordings` 时，PostgreSQL 报错退出：

```text
ERROR: could not resize shared memory segment "/PostgreSQL.53701832" to 67128736 bytes: No space left on device
```

此外，若在 `psql -c "DELETE ...; VACUUM ANALYZE ...;"` 单次命令中串联多条语句，还会触发 `ERROR: VACUUM cannot run inside a transaction block`。

### 根因

1. Docker 容器默认挂载的 `/dev/shm`（POSIX 共享内存）上限仅为 **64 MB（`67,108,864` 字节）**。当表规模达到 100 万行时，PostgreSQL 启动并行 Worker（`Parallel Seq Scan` / 并行 `VACUUM`）尝试通过动态共享内存（DSM）分配约 64.02 MB（`67,128,736` 字节），瞬间突破容器默认的 64 MB 限制。
2. `psql -c` 包含分号分隔的多条 SQL 时，PostgreSQL 默认将整串命令包装在同一个隐式事务块中执行，而 `VACUUM` 不允许在事务块内运行。

### 修复

1. 在 `docker-compose.yml` 的 `postgres` 服务下显式配置 `shm_size: 256mb`。
2. 在自动化脚本中将 `DELETE` 与 `VACUUM ANALYZE` 拆分为独立的 `psql -c` 调用。

### 验证

重建 `postgres` 容器后，100 万行写入、并行 `EXPLAIN (ANALYZE, BUFFERS)` 及 `VACUUM ANALYZE` 全部通过（见 `output/p1-experiments-report.json`）。

## 2026-10-21：容器 `pause`（`SIGSTOP`）故障注入下 TCP 探针假阳性与 Outbox 上下文超时回收

### 现象

使用 `docker compose pause redis` 模拟 Redis 进程卡死时：
1. 仅使用 `net.DialTimeout("tcp", redisAddr, ...)` 的健康检查依然返回 `"redis": "ok"`（假阳性）。
2. 若 `POST /complete` 中的同步派发使用已超时的 `ctx` 调用 `RequeueIfDispatching(ctx, eventID)`，会导致回退 SQL 因 `context deadline exceeded` 失败，Outbox 事件停留在 `dispatching`。

### 根因

1. `docker compose pause` 通过 cgroups 冻结容器内用户态进程（类似 `SIGSTOP`），但容器网络命名空间的 **Linux 内核协议栈仍在工作**，只要 TCP `accept` 队列未满，内核仍会自动完成三次握手，导致 L4 TCP 探针误判存活。
2. 当同步投递因 `ctx` 超时退出时，复用同一个已取消的 `ctx` 去执行数据库的补偿回退必然立即失败。

### 修复

1. `/healthz` 对 Redis 升级为 **L7 应用层探针**：连接建立后设置 500ms 读写截止时间，发送 RESP 协议 `*1\r\n$4\r\nPING\r\n` 并校验返回 `+PONG`。
2. `Dispatcher.requeueSafely` 使用独立的 `context.WithTimeout(context.Background(), 2*time.Second)` 执行 `RequeueIfDispatching`，确保即使上游请求超时取消，Outbox 状态也能可靠回退至 `pending`。

### 验证

`make p1-experiments` 实验 5 验证通过：`pause redis` 期间 `/healthz` 准确返回 `503`（`"redis": "down"`），`POST /complete` 返回 `200 OK` 且 Outbox 保持 `pending`；`unpause redis` 后 1 秒内后台自动补投递并变为 `dispatched`。

## 2026-10-22：切换 Xcode 版本后 `make test-apple-bridge` 在系统头文件上报错

### 现象

`make test-apple-bridge` 在编译 `Bridge/JKMeetingCore.mm` 时，于 `Foundation.framework/Headers/NSZone.h`、`Security.framework/Headers/cssmtype.h` 等 SDK 头文件上报 20 个错误（`-Wunused-parameter`、`-Winvalid-utf8`、`-Wmissing-method-return-type`，均被 `-Werror` 升级为错误）。环境为 macOS 27.0，`xcode-select -p` 指向 `Xcode-27.1.0-Release.Candidate.app`。

### 根因

`apple/cmake-build/CMakeCache.txt` 中的 `FOUNDATION_FRAMEWORK` 仍缓存着旧的 `/Applications/Xcode.app/.../MacOSX.sdk/.../Foundation.framework`。CMake 因此把该 SDK 的 `Frameworks` 目录以 `-F` 用户框架路径传给编译器，而当前编译器来自另一套 Xcode，旧 SDK 的头文件不会被当作系统头文件，警告也就不会被抑制。证据：用 HEAD 版本的 `JKMeetingCore.mm` 加同样的参数编译，同样报 20 个错误；全新构建目录下 `FOUNDATION_FRAMEWORK` 指向 27.1 RC 的 SDK，编译零错误。

### 修复

```sh
cmake -S apple -B apple/cmake-build -U FOUNDATION_FRAMEWORK
make test-apple-bridge
```

### 验证与防回归

修复后 `make test-apple-bridge` 的 6 项测试全部通过。切换 Xcode（`xcode-select -s`）后，凡是遇到 SDK 头文件报警告的情况，先检查 CMake 缓存中通过 `find_library` 得到的框架路径是否仍指向旧 Xcode。

## 2026-10-22：接入 libopus 后 core 测试报 “unused variable”，NEON 配置互相牵连

### 现象

1. 把 libopus 用 `add_subdirectory` 接入 `core/CMakeLists.txt` 后，全新构建的 `make test-core` 在 `streaming_resampler_test.cpp` 上报 `unused variable 'expected'` 等错误（被 `-Werror` 升级）。这些变量只在 `assert` 中使用。
2. 为去掉 libopus 打印的 `ERRORRuntime cpu capability detection needed for MAY_HAVE_NEON`，设置了 `OPUS_MAY_HAVE_NEON=OFF`，结果 `celt/arm/celt_neon_intr.c` 报 `call to undeclared function 'celt_inner_prod_neon'`。

环境：macOS 27.0、Apple M1 Pro、Xcode 27.1 RC、CMake 构建 `core/build`。

### 根因

1. `core/third_party/opus/cmake/OpusBuildtype.cmake` 在 `CMAKE_BUILD_TYPE` 为空时，把它写成缓存值 `Release`。这个设置对父工程同样生效，于是测试定义了 `NDEBUG`，`assert` 被编译掉。证据：构建后 `core/build/CMakeCache.txt` 中 `CMAKE_BUILD_TYPE:STRING=Release`。
2. libopus 只在定义 `OPUS_ARM_MAY_HAVE_NEON_INTR` 时才声明 NEON 内建函数；`OPUS_PRESUME_NEON` 依赖这些声明，不能单独开启（`CMakeLists.txt` 第 560–575 行）。那条 `ERROR...` 来自 `message(ERROR ...)`。`ERROR` 不是 CMake 的消息级别关键字，只会当作文本打印，不会中断构建。

### 修复

- `core/CMakeLists.txt` 在 `add_subdirectory(third_party/opus)` 之前，构建类型为空时设为 `Debug`（缓存值）。`make bench-core` 显式传入 `Release`，不受影响。
- 保持 `OPUS_MAY_HAVE_NEON` 为默认的 `ON`，只额外设置 `OPUS_PRESUME_NEON=ON`；那条 `ERROR...` 文本无害，不需要处理。

### 验证与防回归

全新构建（`rm -rf core/build && make test-core`）后，缓存中 `CMAKE_BUILD_TYPE=Debug`、`OPUS_PRESUME_NEON=ON`，8 个测试套件全部通过；`flags.make` 中带 `OPUS_ARM_PRESUME_NEON`。`apple/scripts/build-opus-xcframework.sh` 会检查每个切片的编译参数都包含 `OPUS_ARM_PRESUME_NEON_INTR`，不包含时直接失败。

## 2026-10-22：`make up-local` 后立刻启动 API，因 S3 未就绪直接退出

### 现象

Colima 刚启动，执行 `make up-local` 后约 10 秒内运行 `make run-server`，API 打印 `检查 S3 bucket 失败：Get "http://127.0.0.1:9000/recordings/?location=": Connection closed by foreign host` 并以退出码 1 结束。同时启动的 Worker 和 Whisper 正常。

### 根因

SeaweedFS 容器状态为 `running` 时，S3 网关（9000 端口）还没开始服务。API 启动时只检查一次 bucket，失败即退出（`server/cmd/api/main.go`）。证据：约 2 分钟后 `curl http://127.0.0.1:9000/` 返回 403（已在服务），直接重启 API 后 `/healthz` 返回 200。

### 修复

属于启动时序问题，未改代码：先轮询 `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:9000/`，返回非 `000` 后再启动 API。

### 验证与防回归

重启 API 后 `AUDIO_FORMAT=ogg make smoke-asr` 通过（P2-2 B7）。如果以后要自动化本地栈启动，在 `up-local` 之后加入 S3 就绪等待，不要依赖固定的 sleep。

## 2026-10-23：Swift 调用 ObjC 桥接对象后 XCTest SIGSEGV，`impl_` 为空

### 现象

P2-3 新增 `JKMeetingOggOpusDecoder` 后，macOS XCTest 在 `OggOpusDecoder::push` 内 SIGSEGV（空指针 `impl_`）。编译器同时警告 “no calls to throwing functions occur within 'try' expression”。

环境：macOS 27.0、Xcode 27.1 RC、Swift 6。

### 根因

桥接类只声明了 `- (nullable instancetype)initWithError:(NSError **)error`。它导入 Swift 后的签名是 `init() throws`，与继承的 `NSObject.init()` 同名。Swift 侧的 `try JKMeetingOggOpusDecoder()` 解析成了不抛错的 `NSObject.init()`，于是没有创建 C++ 对象，`impl_` 保持空值。上面那条编译警告就是证据：`try` 后面实际上没有可抛错的调用。

### 修复

去掉 `initWithError:`，改为覆写 `- (nullable instancetype)init NS_DESIGNATED_INITIALIZER`，在其中创建 C++ 对象，失败时返回 `nil`。同步修改桥接测试和 Swift 调用点。

### 验证与防回归

`make test-apple-bridge` 11/11、macOS/iOS XCTest 42/42 通过。今后给 `NSObject` 子类加无参可失败构造时，不要用 `initWithError:`；如果确实需要错误详情，应带上至少一个参数（如 `initWithConfig:error:`），或者用可失败 `init` 加单独的错误查询。出现“`try` 后没有抛错调用”的警告时，按本问题排查。

## 2026-10-23：本地 API 运行时 `make test-server` 的 outbox 用例偶发失败

### 现象

本地栈中的 API 运行时执行 `make test-server`，`TestClaimPendingClaimsOnlyOnce` 或 `TestClaimPendingReclaimsStaleDispatchingEvent` 偶发失败；单独重跑经常又能通过。

### 根因

测试与运行中的 API 共用同一个 PostgreSQL。API 的 outbox dispatcher 每 500 ms 领取一次 `pending` 和过期 `dispatching` 的事件，会抢在测试之前领走测试刚插入的行。证据：停掉 API 后，`go test ./internal/outbox/ -count=1` 连续 3 次通过；API 运行时同一命令出现失败。P2-4 新增的 `transcode_outbox` 有独立的 dispatcher，只读写自己的表，不是这两个用例失败的原因。

### 修复

未改代码。运行带数据库的 `make test-server` 前，先停掉本地 API（Worker 不领取 outbox，不受影响）。

### 验证与防回归

停掉 API 后 outbox 用例稳定通过。如果以后要在服务运行时跑集成测试，应给测试使用独立的数据库或 schema，不要靠重试掩盖竞争。

## 2026-10-23：HLS 设置 `preferredPeakBitRate` 后 access log 不出现新档位

### 现象

`HLSPlaybackControllerTests` 连接本地栈，对 23.5 秒的录音（每档 4 个 6 秒分片）切换档位，等待 30 秒，access log 的 `indicatedBitrate` 始终停在起播档。

环境：macOS 27.0、AVFoundation、本机回环网络。

### 根因

AVPlayer 起播后很快把全部 4 个分片缓冲完。之后修改 `preferredPeakBitRate` 只影响后续的分片请求，而这时已经没有分片要请求，所以不会切换。证据：同一测试换成 180 秒录音（31 个分片），切换在 17～73 ms 内出现在 access log 中。

### 修复

属于测试输入问题，播放器代码不变：`make smoke-hls` 新增 `LOOP_SECONDS`，档位切换测试使用 `LOOP_SECONDS=180` 生成的录音。

### 验证与防回归

macOS 与 iOS Simulator 的全量 XCTest 中，`testLiveHLSLoadsLadderAndSwitchesVariants` 都通过。测试超时时会输出 access log 和已缓冲区间，便于区分“已全部缓冲”和“服务端问题”。验证档位切换时，内容必须明显长于播放器的前向缓冲。
